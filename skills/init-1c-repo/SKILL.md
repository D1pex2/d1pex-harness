# /init-1c-repo — репозиторий 1С-проекта из серверной базы

Создаёт репозиторий по образцу типового проекта: исходники конфигурации и расширений из серверной базы, каркас каталогов, настройки vanessa-runner, короткий `AGENTS.md` и при необходимости `CLAUDE.md`, документ о процессе, первый коммит и push.

Шаблоны лежат в `templates/` рядом с этим файлом. Перед работой прочитай `1c-skills:db-dump-xml`, `1c-skills:db-list`, `1c-skills:db-cfe-admin` (если нужно узнать список расширений).

## Правила безопасности

- Выгрузка **всегда идёт из тестовой базы**: пользователь присылает только тестовые базы, к рабочей не подключайся и о ней не спрашивай. Подтверждение на выгрузку из тестовой не нужно. Выгрузка только на чтение.
- Пароли и токены **не пиши** в отслеживаемые файлы, в `.git/config`, в URL remote и в сообщения коммитов. Логин и пароль базы — только в `.v8-project.json` (он в `.gitignore`).
- `git push -u <URL с токеном>` записывает URL с токеном в `branch.<ветка>.remote`. Не используй `-u` с URL: пушь без `-u`, затем `git branch --set-upstream-to=origin/main`, либо сохрани токен через `git credential approve`.
- Не меняй `credential.*.allowUnsafeRemotes` и подобные защитные настройки без явного согласия пользователя. Репозиторий в локальной сети по HTTP — решение пользователя.

## Что узнать у пользователя

Спрашивай только то, чего нет:
1. Сервер и имя **тестовой** базы (источник выгрузки и запись в `.v8-project.json`), логин и пароль.
2. Каталог проекта (по умолчанию текущий).
3. Адрес удалённого репозитория (SSH или HTTP) и способ авторизации.
4. Подключена ли база к хранилищу конфигурации (пути `\\...`, пользователь). Если подключена — реквизиты хранилища нужны платформе при каждой операции.

Если пользователь не даёт подключения и выгружает сам, работай в режиме «выгружает пользователь»: шаг 2 пропусти (`.v8-project.json` не создаётся), в шаге 3 дай ему готовые команды ручной выгрузки, в шаге 4 возьми версию платформы по правилу для этого режима. Остальные шаги те же.

## Порядок работы

### 1. Подготовка

- Версия платформы для серверной базы: установи точную полную версию сервера по подтвержденному источнику, например данным администратора или уже полученному сообщению "Различаются версии клиента и сервера". Сверь с установленными клиентами в `C:\Program Files\1cv8\*\bin`, включая ветки 8.3 и 8.5, и выбери совпадающую полную версию. Если версия сервера неизвестна или соответствующего клиента нет, уточни ее или установку у пользователя до выгрузки. Самая свежая установленная версия не является заменой версии сервера. Зафиксируй полный номер и путь `bin`; формат выгрузки задает фактически использованная платформа.
- Если база под хранилищем по сетевому пути: проверь `Test-Path` пути. «Отказано в доступе» (система ошибка 5) означает, что Windows не авторизована на сервере: пользователь должен один раз открыть шару в проводнике или выполнить `net use`. Пока сеть не пускает, платформа пишет «Соединение с хранилищем конфигурации не установлено».
- В проекте Конфигуратор не должен быть открыт в этой базе: иначе «Ошибка блокировки информационной базы для конфигурирования».

### 2. Реестр баз `.v8-project.json`

Создай по `templates/.v8-project.example.json`: `v8path`, база `test` (server/ref, user, password), `configSrc: "src\\cf"`, `extensions[].src`, при хранилище `repository` (путь и пользователь, пароль — только если есть). Файл должен быть в `.gitignore`.

Читай шаблон JSON-парсером, заполняй объект значениями и записывай сериализатором, затем обязательно разбери записанный файл. Не собирай JSON строковой подстановкой или heredoc: пути Windows требуют экранирования. Например, после заполнения объекта `$registry` из шаблона:

```powershell
$registry | ConvertTo-Json -Depth 20 | Set-Content -LiteralPath ".v8-project.json" -Encoding utf8
$verified = Get-Content -Raw -LiteralPath ".v8-project.json" | ConvertFrom-Json -ErrorAction Stop
if ($verified.v8path -ne $registry.v8path) { throw "Путь платформы изменился при записи JSON" }
```

`v8path` заполняй подтвержденным путем `bin` из шага 1, а `configSrc` и пути расширений сохраняй как строки путей после разбора, например `src\cf`. Так же сериализуй и проверяй изменения `autumn-properties.json`.

### 3. Выгрузка

```powershell
$s = "<путь к навыкам>/db-dump-xml/scripts/db-dump-xml.ps1"
powershell.exe -NoProfile -File $s -V8Path "<bin>" -InfoBaseServer <сервер> -InfoBaseRef <база> -UserName "<логин>" -Password "<пароль>" -ConfigDir "<проект>\src\cf" -Mode Full
powershell.exe -NoProfile -File $s -V8Path "<bin>" ... -ConfigDir "<проект>\src\cfe" -Mode Full -AllExtensions
```

`-AllExtensions` кладёт каждое расширение в свой подкаталог `src/cfe/<Имя>`. Каталог должен существовать (с `README.md` из шаблона — это нормально).

Режим «выгружает пользователь»: дай команды конфигуратора, каталоги `src\cf` и `src\cfe` создай заранее.

```powershell
& "<bin>\1cv8.exe" DESIGNER /S"<сервер>\<база>" /N"<логин>" /P"<пароль>" /DumpConfigToFiles "<проект>\src\cf" /Out "<проект>\dump-cf.log"
& "<bin>\1cv8.exe" DESIGNER /S"<сервер>\<база>" /N"<логин>" /P"<пароль>" /DumpConfigToFiles "<проект>\src\cfe" -AllExtensions /Out "<проект>\dump-cfe.log"
```

Проверь результат: список подкаталогов `src/cf` и `src/cfe`, версию из `Configuration.xml` (`<Version>`) у конфигурации и расширений.

### 4. Каркас проекта

Скопируй `templates/` в проект (не перезаписывая существующее):
`.gitignore`, `.v8-project.example.json`, `autumn-properties.json`, `packagedef`, `docs/`, `examples/`, `features/`, `fixtures/`, `lib/`, `tasks/`, `tests/`, `tools/`, `vendor/`, `src/**/README.md`.

Затем:
- `AGENTS.md` — из `templates/AGENTS.md`, подставь `{{PROJECT}}` (имя), `{{PLATFORM}}` (полная версия платформы, фактически выполнившей выгрузку), `{{PROJECT_DESCRIPTION}}` (например, «ПримерПроекта» 1.3 (разработчик)), `{{EXTENSIONS_LIST}}` (строки вида ``- `src/cfe/<Имя>` — расширение``), `{{CHANGE_POLICY}}` (**всегда спрашивай в чате свободным текстом**, что писать про доработки основной конфигурации; не предлагай готовых вариантов и не подставляй по умолчанию; по ответу пользователя сформулируй короткое правило сам).
- `CLAUDE.md` - из `templates/CLAUDE.md`, только если пользователю нужна поддержка Claude. Это отдельный файл со ссылкой `@AGENTS.md`; основной `AGENTS.md` содержит правила и не заменяется ссылкой на себя.
- `docs/workflow.md` не создавай: процесс описан в `AGENTS.md`.
- `autumn-properties.json`: `v8version` ставь полной версией установленной платформы, которой делал выгрузку (например `8.3.27.2074`): короткая `8.3.27` подхватывает другой клиент и даёт предупреждение о разных версиях клиента и сервера. Используй подтвержденную полную версию из шага 1; `ibconnection` по умолчанию локальная `/F./build/ib`. Если выгружал пользователь, уточни у него полную версию фактически использованной платформы или возьми ее из подтвержденного лога выгрузки. Атрибут `version` в XML задает формат, а не точную сборку платформы. Пока сборка неизвестна, не подставляй свежую установленную версию в `v8version` и `{{PLATFORM}}`, не выдавай эти настройки как готовые.

Проверь каркас: в заголовке `AGENTS.md` указана фактическая версия, подстановок `{{...}}` не осталось, основной файл содержит правила. Если создан `CLAUDE.md`, ссылка на `AGENTS.md` находится только в этом отдельном файле.

В `AGENTS.md` **не пиши** серверы, имена баз, пути хранилищ и пароли. Файл короткий: что за проект, что лежит в `src`, процесс, правила. Не дублируй общие правила из глобальных инструкций.

### 5. Инструменты (необязательно, при согласии)

- vanessa-runner требует OneScript 2.x (`ВерсияСреды("2.0.0")` в `packagedef`). Если стоит 1.x: скачай `OneScript-<версия>-win-x64.zip` с GitHub `EvilBeaver/OneScript` в `%LOCALAPPDATA%\OneScript\<версия>`, добавь `bin` в пользовательский PATH перед старым. Системную установку не затирай без согласия.
- Зависимости: `opm install -l` в корне проекта (в `oscript_modules`, он в `.gitignore`). Проверка: `oscript_modules\bin\vrunner.bat --help`.
- В PATH не добавляй `oscript_modules\bin` проекта: путь привязан к каталогу.
- **Что проверять:** если пользователь пишет, что дорабатываются только расширения, запускай синтаксическую проверку только расширений (без основной конфигурации); если дорабатывается основная конфигурация, проверяй основную. Выбор цели: `--target AllExtensions` (все расширения), `--target main` (основная), `--target <ИмяРасширения>` (одно); без `--target` проверяется всё. Версию платформы задавай полностью (`--v8version 8.3.27.2074`), иначе возможно предупреждение о разных версиях клиента и сервера.
- `vrunner validate syntax-check` на серверной базе: `--ibconnection "/S<сервер>/<база>" --db-user ... --db-pwd ... --v8version <полная версия, например 8.3.27.2074>`. Замечания про хранилище и «возможно ошибочное свойство» часто шум для обычного приложения; режимы проверки (`ThinClient`, `WebClient`) настрой под проект.

### 6. Git

```powershell
git init -b main
git add -A
git commit -m "Начальная выгрузка конфигурации <Проект>, расширений и настроек проекта"
git remote add origin <URL без токена>
```

Перед `git add -A` проверь, что в индекс не попадут `.v8-project.json`, `build/`, `oscript_modules/`, `*.log`, `mcp-server.log*` (лог MCP-сервера в корне проекта, явно указан в `.gitignore`) (`git check-ignore -v`) и нет паролей: `Select-String` по проекту без `src/` на известный пароль. Сообщение коммита — по-русски, о сути выгрузки; строку соавторства (`Co-Authored-By`) добавляй по общим правилам пользователя.

Push:
- **SSH**: сначала пользователь сам подтверждает ключ хоста (`ssh -T git@host`); автоматически ключ не принимай.
- **Токен GitLab уже сохранён в системе пользователя** (Диспетчер учётных данных Windows): сначала просто пробуй `git push origin main` с `GIT_TERMINAL_PROMPT=0`, токен не запрашивай. Если пройдёт, затем `git branch --set-upstream-to=origin/main main`.
- **HTTP/HTTPS с токеном**: токен даёт пользователь (Personal Access Token с `write_repository`). Передай его один раз в команде: `git -c credential.helper= push "<URL_WITHOUT_CREDENTIALS>" main` (без `-u`), после этого `git config branch.main.remote origin`, затем `git fetch origin` и `git branch --set-upstream-to=origin/main`. Если пользователь просит сохранить токен глобально — `git credential approve` (хранится в Диспетчере учётных данных Windows, не в файле). Токен потом советуй отозвать, если он был показан в чате.
- Git Credential Manager блокирует HTTP для GitLab («Unencrypted HTTP is not recommended»): разрешение даёт только пользователь (`credential.http://host.allowUnsafeRemotes true`).
- Репозиторий на сервере должен существовать и быть пустым.

### 7. Итог пользователю

Коротко: что выгружено (версии), что создано, что осталось на его стороне (токен, хранилище, загрузка в тестовую). Если база подключена к хранилищу, напомни: полная загрузка из XML в такую базу невозможна, только частичная по захваченным объектам, либо получение из хранилища.

## Известные подводные камни

- `db-dump-xml -Mode Changes` отказывает без `ConfigDumpInfo.xml` или при другой версии формата — `Full` делай осознанно.
- Загрузка конфигурации в базу под хранилищем: «Загрузка невозможна: текущая конфигурация помещена в хранилище». Для проверки состояния тестовой базы относительно хранилища: `db-repo report`, `db-repo update` (получает недостающие версии, затем `db-update`).
- `LF will be replaced by CRLF` при `git add` — предупреждение, не ошибка. Не трогай автокрлф без просьбы.
- Не перезаписывай существующую эталонную выгрузку в репозитории новой выгрузкой из тестовой базы без явной просьбы.
