# Дополнения к superpowers

Навыки superpowers - чужой плагин, его обновление сотрёт правки на месте. Здесь лежат только дополнения.
Каждое правило применяй вместе с тем навыком, к которому оно относится. Перед передачей результата перечитай применимые пункты и сверь с конкретным решением; наличие нужной фразы в отчете не доказывает выполнение.

## brainstorming

- Перед выбором визуальных направлений рабочего экрана спроси, есть ли привычное приложение или образец, на который пользователь хочет ориентироваться, и какого сходства хочет избежать. Уже названный образец используй без повторного вопроса; сначала уточни нужные свойства образца, затем предлагай варианты. Отсутствие образца не мешает предложить собственное направление.

- **Заказчик не разработчик.** Если собеседник - заказчик или он уже отдал технический выбор агенту, варианты описывай через последствия, которые он заметит: скорость на телефоне, внешний вид, цена доработок, кто сможет поддерживать. Названия технологий давай в скобках. Если выбор уже делегирован, предложи одну рекомендацию на подтверждение, а не меню.
  Пример: не «Vite + Svelte или React», а «быстро открывается по мобильной сети, доработки дешевле (Svelte)».
- **Предметные термины только из источника.** Значение поля данных бери из его синонима или комментария в метаданных, из кода или от пользователя. Если поле названо нейтрально («Количество»), а смысл выводится только из того, как его использует код, пиши в текстах для людей название поля («количество из матрицы точки»). Свою трактовку («упаковка») задай вопросом, а не закладывай в спецификацию.
- **Утверждения о платформе.** Каждое утверждение о поведении платформы или фреймворка, после которого из работы что-то выпадает («права не нужны», «так нельзя», «режим не мешает»), подтверди образцом в репозитории (grep аналогичного объекта) или документацией (для 1С - bsl-context) и укажи рядом строку «Источник: ...». Без источника пометь его как предположение. Для каждой новой операции, которую платформа ограничивает (HTTP, файлы, COM, внешние компоненты, привилегированный режим), перечисли точки входа и режим каждого расширения на пути вызова (безопасный режим, профиль безопасности). Хук Stop проверяет изменённые спеки и планы на такие утверждения без источника.

## writing-plans

- Для текстового детектора или фильтра при наличии реального корпуса до реализации получи независимую грубую выборку по ключевым словам с контекстом и разбери как срабатывания, так и пропуски. Формы из корпуса превращай в безопасные тестовые примеры без действующих секретов и персональных данных. Перед защищаемой публикацией проверь ложные пропуски, а не только ложные срабатывания; в Review Focus плана укажи происхождение набора и ограничения выборки.

- **Посчитали и потратили.** Если одна задача плана вычисляет величину (лимит, бронь, квота, потребность), а другая её расходует, в Review Focus обязательна строка: «пограничные строки источника (ноль, отрицательные, пустые) на стороне расчёта и на стороне расхода обрабатываются одинаково», и к ней тест в задаче-потребителе.
- **Self-Review: утверждения о платформе** - то же правило, что в brainstorming: источник рядом с утверждением или пометка «предположение» и строка в Review Focus.
- **Модель ревью вместе со способом выполнения (только для Claude Code).** В том же сообщении, где спрашиваешь способ выполнения (Subagent-driven или Native), спроси, какой моделью делать ревью. Имена моделей не зашивай: предложи две самые передовые модели Codex на момент вопроса - первые две по полю `priority` (меньше - выше) среди записей с `visibility: list` в `~/.codex/models_cache.json` (отметь, какая стоит в `~/.codex/config.toml`). Если одна из них из семейства Astra, так и подпиши: выбор пользователем считается разрешением на нее для этого плана. Третий вариант - субагент Claude. Если способ выполнения уже выбран, задай вопрос о модели ревью отдельно до первого ревью. Ответ запиши в журнал плана; разрешение на Astra действует только для этого плана.

## subagent-driven-development

- **RED обязателен, а не оговорка.** Отчёт исполнителя без раздела «RED: команда / вывод / причина падения», где падение вызвано отсутствием реализации, контроллер не отправляет на ревью: возвращает исполнителю. Если тесты писались вместе с кодом, исполнитель доказывает их силу мутацией: временно убирает ключевую ветку и показывает падающий тест. Статус DONE_WITH_CONCERNS этот шаг не заменяет.
- **Ревью через Codex (только для Claude Code; Codex это правило пропускает).** Ревью задач и итоговое ревью ветки контроллер отдает Codex, чтобы экономить токены: агент `codex:codex-rescue` в режиме только чтения (без `--write`), модель та, что пользователь выбрал вместе со способом выполнения (см. writing-plans); без выбора - без `--model`, из `~/.codex/config.toml`. Перед первым запуском в сессии проверь, что модель в конфиге не из семейства Astra; Astra передавай через `--model` только при явном разрешении пользователя на этот план. В задании Codex - пути к брифу, отчету исполнителя, diff-файлу ревью, глобальным ограничениям и формат ответа из шаблона ревьюера (вердикт по спеке, Critical/Important/Minor с file:line, итог). Повторное ревью после исправлений - тоже Codex. Если Codex недоступен или вернул пустой ответ, ревью делает субагент Claude, и об этом сообщается пользователю.
- **Фейк внешней системы - из записи.** Если задача заменяет вызов внешней системы и в брифе есть записанный реальный ответ, фейк строится из этой записи (загрузкой файла или копией полей), а не из старого фейка. Тест сверяет ключи и заголовки таблиц фейка с записью. В брифе ревьюера задачи - отдельный пункт: «фейк совпадает с записанным ответом по ключам и заголовкам».

## test-driven-development

- **Фейк, расходящийся с протоколом,** делает тест доказательством фейка, а не кода. Фейк строй из записанного реального ответа или проверяй по нему автоматически.
- **Эталон на другом языке** повторяет арифметику платформы. Для 1С: `Окр(x, n)` округляет половину вверх, а Python `round` банковский и работает с двоичной дробью, поэтому в эталоне `Decimal(repr(x)).quantize(Decimal('0.001'), ROUND_HALF_UP)`. В набор входов включай хотя бы одно значение ровно на половине.
