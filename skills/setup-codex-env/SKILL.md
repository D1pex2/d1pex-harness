# Настройка среды Codex

1. Проверь `codex --version`, `codex doctor --help`, `codex plugin --help`, `codex mcp --help`. Используй синтаксис установленной версии. Десктопное приложение обновляй его штатным механизмом; не устанавливай поверх него другую сборку CLI.
2. Определи, что уже установлено. Согласованный состав выполняй без повторных разрешений. Перед заменой настроек сохраняй резервную копию в защищенном каталоге пользователя. Не выводи заголовки авторизации и токены.
3. Для Git, VS Code, Python и платформы 1С проверь фактическую потребность задачи. Не ставь Java ради bsl-context, если используется Rust-реализация. Платформу 1С автоматически не устанавливай и не выбирай за пользователя серверную версию.

## Навыки и плагины

- Предпочитай один источник каждого набора. Пользовательские навыки этого окружения хранятся в `~/.agents/skills`. Не создавай вторые копии в `~/.codex/skills`.
- Superpowers в этом окружении установлен локально в `~/.agents/skills`. Не включай одновременно его копии из разных маркетплейсов. Перед сменой источника сравни и сохрани локальные изменения.
- Доступные встроенные плагины и сервер `node_repl` принадлежат приложению. Не подменяй их параметры вручную.
- cc-1c-skills подключай из подтвержденного пользователем источника. Перед командами установки или обновления сверяй `--help`.
- Учетные каталоги `synced` управляются синхронизацией. Их файлы не удаляй для устранения дублей; отключай конкретную вторую копию в настройках после сравнения.

## MCP

Сначала прочитай существующие блоки `mcp_servers` в `~/.codex/config.toml`. Сохраняй действующие параметры и ключи; добавляй только согласованные подключения.

Для bsl-context выбери реализацию по существующей конфигурации. В текущем окружении используется `bsl-context-rs.exe` с `--config`. Перед изменением формата прочитай README именно установленной версии. Источники имен конфигураций бери из существующих индексов code-index; проверяй `symbol_sources_status` и состояние конкретного репозитория. Не подменяй Rust-сервер старым JAR.

Список клиентских баз не является частью установочного навыка. Адреса, алиасы и секреты бери из настроек выбранного проекта или от пользователя. Тестовую базу обозначай суффиксом `-test`. Не одобряй автоматически все инструменты базы: права чтения и записи различаются. Секреты не вставляй в примеры, журналы или файлы навыка.

## Правила и хуки

Сохраняй текущий `AGENTS.md`. Не заменяй его снимком `rules.md` из установочного комплекта. Изменения правил показывай как точечные различия.

Пользовательские хуки one-c-rules.js подключают только правила 1С по признакам проекта или инструментам, без списка клиентов. Детектор one-c-detector.js расположен рядом с хуком; внешние наблюдатели не требуются. При переносе окружения настрой абсолютные пути этого пользователя и проверь хуки на временном проекте.

## Проверка результата

Проверь разбор TOML/JSON, существование исполняемых файлов и `codex doctor`. Сетевые ошибки из песочницы отделяй от подтвержденных неисправностей. Для измененных MCP проверь живое соединение, а не только наличие записи в конфигурации. Напомни, какие изменения требуют нового чата или перезапуска приложения. Базы 1С проверяй только в согласованном объеме.

## Совместимость запускателей 1С

Перед выбором OneScript проверь минимальную версию установленного пакета vanessa-runner. Используй совместимый интерпретатор, найденный на машине пользователя. Не заменяй глобальный PATH, если он нужен старым пакетам. После восстановления oscript_modules проверь bat-файлы: пакетный менеджер может перегенерировать их. Проверка: локальный `vrunner.bat --version`.

Testpilot и другие вспомогательные инструменты используй из существующей среды пользователя либо установи по их документации в согласованном объеме. Не подставляй пути с машины автора навыка. Для bsl-context используй платформу конкретного проекта и его индекс; новый MCP для этого не нужен.
