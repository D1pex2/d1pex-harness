# Архитектурные приемы доработок 1С

Выбирай структуру по назначению расширения и действующей реализации. Применяй вместе с `1c-development-rules`: поиск точки изменения, контексты исполнения, разрешения и проверки задаются там.

## Формы и назначение расширения

- В существующем расширении используй его действующий механизм модификации форм и вспомогательные функции. Сначала проследи вызовы от обработчика до реализации.
- При создании расширения общих доработок вроде `РТ_Доработки`, предназначенного для регулярного изменения разных форм, предусматривай общий механизм их модификации. Распознавай назначение по составу задач, а не только по имени.
- В узком расширении небольшую доработку можно оставить в обработчике формы. Вынос выбирай при повторном использовании или самостоятельной сложности задачи.

Пример организации расширения общих доработок:

1. Обработчик заимствованной формы передает ее контекст существующей точке модификации.
2. Общий модуль модификаций выбирает процедуру нужной формы.
3. Процедура строит интерфейс через принятые вспомогательные функции расширения.

Если в проекте есть отдельный диспетчер событий форм, сохраняй его. В новом расширении отдельный модуль-посредник не обязателен: достаточно понятной общей точки модификации. Повторный вход учитывай в том же механизме, например проверкой наличия собственного элемента.

Каждое расширение имеет свою область ответственности. Общая библиотека для нескольких расширений требует отдельного решения о зависимостях и поставке. Несколько одинаковых вспомогательных функций сами по себе такого решения не требуют.

## Владелец бизнес-операции

Разделяй построение интерфейса и бизнес-операцию. Правило, используемое несколькими формами или командами, размещай у существующего владельца: в модуле объекта, менеджере или предметном общем модуле по архитектуре проекта. Форма собирает ввод, вызывает операцию и показывает результат.

Пример: изменение периода плана отчетности проверяет допустимые границы и меняет связанные данные в одном предметном методе. Две формы вызывают этот метод вместо собственных вариантов проверки и изменения.

Для небольшой локальной операции дополнительный слой не нужен. Полезность выноса определяется ответственностью и использованием, а не длиной метода сама по себе.

## Сложная загрузка файла

Когда загрузка содержит несколько самостоятельных этапов, выделяй чтение файла, проверку и сопоставление данных, подготовку и запись документов. Сохраняй номер исходной строки, чтобы результат можно было связать с входными данными.

Если параметры и результаты передаются между этапами, используй единое описание их структуры. Различай успешную обработку строки, отсутствие соответствия, неоднозначное соответствие и ошибку. Сложная загрузка не означает автоматической необходимости фонового задания, универсального конвейера или определенного размера транзакции: эти решения выбираются по задаче и действующему механизму проекта.

## Интеграции

При добавлении операции в существующую интеграцию сохраняй разделение: транспорт выполняет HTTP-обмен, модуль сервиса знает его адреса, авторизацию и формат данных, предметная операция использует полученный результат. Используй имеющийся транспорт и конструктор параметров. Отдельную универсальную систему адаптеров для единичного запроса не вводи.

## Проверка выбора

Перед реализацией кратко назови владельца операции, существующую точку подключения и основание для нового модуля, если он нужен. При доработке сохраняй согласованные границы: применение приема не дает разрешения перерабатывать соседний код или менять зависимости между расширениями.
