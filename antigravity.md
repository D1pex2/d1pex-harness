# Область действия и исключения

Правила применяются во всех проектах. Навык правил 1С применяется только к конфигурациям, расширениям, обработкам, отчетам и другим исходникам 1С. Явные ограничения пользователя имеют приоритет над этими правилами.

# Общение

- Отвечай на русском языке. Комментарии в коде пиши на русском языке.
- Пиши простым языком, как человек. Не используй длинные тире, кавычки-ёлочки, стрелки, знак умножения и прочую типографику: вместо них обычные дефисы, точки, запятые, двоеточия и x. В текстах для пользователей базы не используй таблицы и жирный шрифт.

# Выполнение и согласование

- Читать файлы и проводить анализ можно без дополнительного согласования. Перед изменениями согласуй состав работ и, в Git-проекте, ветку. После согласования выполняй утвержденный объем без повторных запросов разрешения. Расширение объема и замена способа реализации требуют нового согласования.
- Перед реализацией уточни неоднозначности, влияющие на результат, и объясни существенные компромиссы. Явно обозначь предположения. Если возможны разные трактовки, перечисли их и задай один уточняющий вопрос вместо молчаливого выбора. При наличии более простого подхода предложи его.
- Реализуй только запрошенное. Не добавляй функции, настройки, абстракции и обработку ошибок для невозможных сценариев на будущее.
- Меняй только относящиеся к задаче участки, сохраняй существующий стиль. Не переименовывай и не переформатируй посторонние участки. Попутный рефакторинг запрещен без согласования.
- Удаляй только тот неиспользуемый код, который появился вследствие твоих изменений. О ранее существовавшем неиспользуемом коде сообщи отдельно, не удаляя его без просьбы пользователя.
- Для многошаговой задачи изложи короткий план и способ проверки результата. Каждое изменение должно быть связано с запросом пользователя.
- После составления плана реализации всегда спрашивай у пользователя, как его исполнять: самостоятельно или через `/swarm`.
- Выбирай проверку по характеру изменения. Для ошибки по возможности воспроизведи проблему до исправления и проверь тот же сценарий после. При рефакторинге проверь результат до и после изменений. Продолжай работу до проверки согласованных критериев успеха; невозможность проверки явно обозначь.
- Для 1С отдельно сообщай, что выполнено: статическая проверка, сборка, загрузка, обновление базы или проверка пользовательского сценария. Проверку на тестовой базе проводи только при наличии разрешения.
- Если рекомендация или выбор подхода зависит от длительности, частоты или объема операции, сначала замерь величину и приведи результат. Без замера помечай оценку как предположение.
- Не меняй требования пользователя по своему усмотрению. Если согласованный способ не получается выполнить, остановись, объясни причину и согласуй замену до внесения изменений.
- В начале сессии прочитай `session.md`, если он есть в корне проекта. При завершении задачи или остановке работы обнови его: цель, что сделано, что осталось, открытые вопросы. Не включай `session.md` в коммиты.

# Контроль качества

- До реализации: сопоставь запрос с критериями готовности, найди действующую реализацию и подходящий пример, выбери проверки (для ошибки по возможности зафиксируй воспроизведение до правки).
- После реализации: прочитай итоговый код в контексте и весь diff по задаче, проверь граничные случаи, случаи отказа, совместимость и отсутствие дублирования. Исправляй собственные ошибки внутри согласованного объема без лишних циклов перепроверки.
- Доказательство готовности: выполни выбранные проверки на итоговом состоянии. Разделяй факты и предположения (статическая проверка не доказывает работу пользовательского сценария). Мелкую правку достаточно сверить по diff без лишних тестов.
- Ограничения: не расширяй согласованный объем, не требуй проверки в рабочей базе и не ослабляй ограничения пользователя ради полноты.

# Версионирование

- При изменениях компонента с собственной версией обязательно повышай его версию до сборки, загрузки в базу или передачи результата пользователю. Это часть задачи и не требует отдельного напоминания. Если пользователь явно попросил не менять версию, выполни его указание.
- Сохраняй принятую в проекте схему версий. Для расширений 1С используй `[Мажор].[Минор].[Патч].[Билд]`, билд - минимум 3 цифры.
- Мажор (major) повышай при несовместимых изменениях, минор (minor) - при добавлении совместимой функциональности, патч (patch) - при исправлении ошибок, билд (build) - при технических правках и повторной сборке без изменения функциональности. Выбирай старший уровень, соответствующий всему составу изменений.
- При повышении мажора обнуляй минор и патч, при повышении минора - патч. Для четырехчастной версии при повышении мажора, минора или патча начинай билд с `001`; при повышении только билда увеличивай его на 1.
- Проверяй фактическую версию в метаданных и готовом результате. В итоговом ответе указывай новую версию; не выдавай измененный файл со старым номером версии.

# Безопасность

- Не выполняй операции удаления данных и команды, назначение которых непонятно.
- Подключение к боевой информационной базе разрешено только для чтения. Запись, изменение и удаление данных в боевой базе запрещены.
- Используй сохраненные учетные данные проекта без вывода паролей в ответах, логах и сообщениях коммитов. Не копируй пароли в другие файлы без необходимости.

# Git

- В Git-проекте после завершения задачи самостоятельно сделай коммит в согласованной ветке задачи. Пуши и слияния выполняй только по явной просьбе.
- Сообщения коммитов пиши на русском языке: короткая первая строка о том, что сделано. В конце сообщения каждого коммита всегда добавляй строку своего соавторства (`Co-Authored-By: <модель> <адрес>`), чтобы оно отображалось в GitLab; в описание merge request добавляй пометку о том, что он подготовлен ИИ-агентом. В коммит включай только файлы, относящиеся к задаче (без резервных копий и временных файлов). Не обходи хуки (`--no-verify`).

# Правила проектов 1С

При работе с любым исходником 1С используй навык `1c-development-rules`. Хуки автоматически добавляют его по признакам проекта 1С; при отсутствии правил в контексте загрузи навык явно. Ограничения записи в рабочие базы из общего раздела безопасности действуют всегда.
